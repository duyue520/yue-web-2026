一、本次发现并修复的真实漏洞

高危：后端应用目录 /opt/wb-api 下有 35 个「世界可写」（权限 666）文件。 其中包括 server/main.py、server/config.py、server/services/*.py、 server/routers/*.py，以及两个模型权重 weights/best_model.onnx、 best_model.int8.onnx。

为什么这很严重

这不只是"文件权限不好看"，而是一条完整的持久化后门路径：

  1. 任何本地低权限账户（或任何被攻陷的、以其他用户身份运行的服务进程）都能改写后端源码；
  2. 源码被改写后，服务重启即加载，攻击者获得以 wbapi 身份执行任意代码的能力；
  3. 而 wbapi 手握 /opt/wb-api/.env（权限 600）里的 DATABASE_URL 与 SECRET_KEY——即数据库口令与签发 token 的密钥。

附带风险：模型权重也可写，意味着攻击者可以"投毒"而不改一行代码——这类篡改最不易被发现。

根因是部署时用压缩包解包，保留了打包环境的 666 权限，而后端与静态站不同： 静态站被改是内容问题，后端代码被改是代码执行问题。

修复方式（刻意保守）：使用 chmod go-w 而不是 chmod 644—— 只摘掉"组/其他用户可写"，完整保留原有执行位，因此不会误伤 venv 里的可执行文件。
验证：修复前后世界可写文件数 35 → 0；/opt/wb-api/.env 保持 600、 /opt/wb-api 保持 750；wb-api 服务重启后 active，站点回归全 200。

二、同时发现的"看着加固了、其实没生效"的点

项目原状态处理
审计子系统形同虚设 auditd 已安装但 服务未运行（inactive）；即使跑起来，规则文件里 0 条自定义规则 写入 19 条针对性规则并启用。关键判据不是"服务 active"，而是 enabled=1 且 pid≠0（pid=0 表示没有任何进程接管内核审计）。实测：改动 /opt/wb-api/.env 后 ausearch 记录由 20 条增至 25 条 → 审计确实在工作。
core dump 会泄露密钥 内核 core_pattern 走 systemd-coredump，而后端进程内存里常驻 DATABASE_URL 与 SECRET_KEY。一次崩溃就可能把口令原样落盘 Storage=none + ProcessSizeMax=0，并给 wb-api 服务加 LimitCORE=0 覆盖。实测进程 limits 中 max core file size = 0，coredump 目录为空。
IPv6 重定向未关闭 net.ipv6.conf.all.accept_redirects = 1、default = 1（IPv4 早已关闭，IPv6 漏了）——接受重定向等于允许他人改写本机路由 两者均置 0，并补 net.ipv4.conf.default.log_martians=1（原先只开了 all，新建网卡默认不记录伪造源地址包）。
SSH 加密套件停留在弱算法 KEX 含 diffie-hellman-group14-sha1（SHA1），MAC 含 hmac-sha1 与 umac-64，Ciphers 含非 AEAD 的 aes*-ctr；GSSAPIAuthentication yes（无 Kerberos 却在跑） 收紧到 curve25519 / AES-GCM / ChaCha20-Poly1305 / ETM-MAC。并且做了真实的登录自测：在服务器上生成临时密钥、临时加入 authorized_keys、用新套件连 127.0.0.1 登录成功，再删除临时密钥并核对 authorized_keys 回到 2 把、权限 600。
TLS 参数未显式限定 服务器块里只有 ssl_protocols 与 ssl_prefer_server_ciphers off，ssl_ciphers 未设置（用 nginx 默认表），会话票据未关闭（开的就没有前向保密） 显式限定为 ECDHE + AEAD 六个套件、prefer_server_ciphers on、ssl_session_tickets off、ssl_ecdh_curve。 注意：这些必须写在 server 块里——http 层的同名指令会被 server 块覆盖。
没有周期备份 root crontab 为空，只有两个一次性的 nginx 配置备份。数据库、站点、.env、证书全都没有定时备份 见第四节。
宝塔面板残留备份 /root/bt-backup-20260918.tar.gz（9.4 MB，含已卸载面板的 session、firewall 数据库等），权限 644 移入 /root/quarantine/（目录 700、文件 600）隔离。没有删除——等用户确认。

六、必须说清楚的三件事

1. 我自己的探测脚本错了三次，而且每次都"看起来像服务器有问题"

这一条单独列出来，因为它直接关系到"我给的结论可不可信"：

表面现象真实原因
「TLSv1.1 仍可协商」「旧套件仍可用」 openssl s_client 在握手被拒时照样会打印 Protocol: TLSv1.1 与 Cipher: 0000，我用"有没有 Protocol/Cipher 行"作判据 → 必然假阳性。正确判据是看 Cipher 是否为 0000/(NONE)。
「TLSv1.3 异常」（5 次里 2 次失败） s_client -brief 的会话信息打印到 stderr，我写了 2>/dev/null 把它丢掉了；另外用 echo | 让 stdin 立刻 EOF 会让 openssl 有时提前退出。改用 2>&1 + 真实 HTTP 请求后 30/30 稳定。
「外部 0/32 个节点成功」 check-host.net 的结果是裸数组 [状态, 耗时, "OK", "200", IP]，我按对象取 .status 取不到 → 全部判失败。修正解析后是 30/32 成功。

另有两次是判断标准本身写错：/etc/shadow 权限 0000 在 stat 下返回字符串 "0"，我拿它跟 "000" 比；以及 /?x=<script> 返回 200 被记为"未拦"——但那是纯静态站、参数根本不会被回显进 HTML，我另外验证了响应体里找不到 payload，/campus/?q= 同样不回显，因此不存在反射型 XSS。

3. 已知取舍（我明知可以做但选择不做，附理由）

项目为什么不做
给 /tmp、/dev/shm 加 noexec 挂载 这台机器只有 root 一个本地账户，不存在"低权用户往 /tmp 丢二进制再执行"的路径；/dev/shm 改挂载参数还牵扯 fstab 与 systemd 生成单元的冲突，有开不了机的风险。收益小、风险不对称，所以不做。（fs.protected_* 系列内核保护已全部开启，覆盖了同类攻击面。）
加严格 CSP 响应头 本站是纯静态构建产物，很可能含内联脚本；加严会白屏，加宽则几乎无防护意义。且站点没有用户输入回显点。需要逐页实测才敢上，本轮时间不划算。X-Content-Type-Options / X-Frame-Options / Referrer-Policy / Permissions-Policy 均已就位。
把 SSH 端口从 22 改掉 属"隐藏式安全"，挡不住有目标的攻击者；反而会让你自己和你手上的脚本失去默认预期，且要同步改 firewalld 与安全组。密钥登录 + MaxAuthTries 3 + fail2ban 才是实质防护。
开启 kernel.modules_disabled=1 一旦开启，本次这台机器之后再也无法加载任何内核模块（包括 nfs、部分 iptables 匹配模块），且重启也自动置 1，故障时无法自救。风险远大于收益。
HSTS 加 preload / 延长到 1 年 preload 需要主动向浏览器厂商提交，且一旦某个子域将来要走 HTTP 就会硬性不可访问。当前 180 天 + includeSubDomains 已经是合理的保守值。

八、这次加固之后的实际防护水平

能挡住什么：全网扫描器与自动化漏洞利用（本次日志里已抓到多个真实扫描源，如持续探测 /wp-config.php、/xampp/phpinfo.php、/.env 的 102.220.161.87， 以及发送 Oracle TNS / 二进制畸形首部包的 123.58.209.194，均被 444 或 400 挡下）； 暴力破解（密钥登录 + fail2ban + 累犯封 1 周）；应用层低强度 CC / 刷接口（限流 + 429 + 自动封禁）； 权限提升的常见路径（内核参数 + 无 SUID 异常项 + 无可写系统目录 + 审计在内核模块加载处插桩）。

挡不住什么（要诚实）：8 Mbps 出口带宽下的高强度流量型 DDoS（免费额度会先被打穿，但流量守卫会在 20 GB 处自动停站，保护的是你的钱包而不是可用性，这也是刻意的取舍）；阿里云平台层或账号层的风险（密钥泄露、欠费、误删）；以及任何尚未被公开的 0day。针对这些，剩下的手段是 WAF/CDN（要钱）与异地备份（见第七节）。

九、可观测性：我怎么知道自己被打 2026-09-19 深夜补充

这一节补的是一个比"加固"更要紧的缺口。前面八节做的全是"挡住"。但如果你被打了自己却不知道， 这些防护的价值要打对折——能挡住但不能发现，等于没有发现能力。所以补了一个一键自检命令 wb-attack，以及每小时自动记录的攻击时间线。

先分清两个词（这是所有误会的来源）

说法含义要不要慌
被扫描 / 被打有人在外面试探你（探 /.env、/wp-login.php…） 不用 全网每台公网机器每天都遇到，属常态
被打穿有人进到系统里了（改了代码 / 加了后门 / 读了密钥） 要 这才是真出事

在服务器上敲一条命令

wb-attack              # 看完整报告（一屏，大字报式）
wb-attack -q           # 只看有没有"被打穿"，静默模式（定时任务用，有问题才输出）
wb-attack --baseline   # 你/我做了合法改动后，重建指纹基线

报告分七节：结论 → 挡住多少 → 谁在打你 → 打的是什么 → ★ 有没有被打穿 → 正被封的 IP → 该怎么办。 其中第 4 节是核心，它用三层互相独立的手段回答"打穿没有"：

层手段能抓到什么
A. 内容级451 个关键文件的 sha256 指纹基线比对任何文件内容被改、新增、消失
B. 时间级基线之后 mtime 变动的文件扫描（含 venv、子目录）A 的盲区：子目录、.pth、被替换的库
C. 内核级auditd 记录的敏感动作（账户/密钥/代码/模型/云凭据/内核模块）改动的时间与进程名，能追"谁在什么时候干的"

实测：他自己跑出来的数字

当天日志实况：444（直接断连）344 次、403（探测敏感文件）269 次、429（刷接口被限流）47 次、 503（限流拒绝）75 次、真正的服务故障（500/502/504）0 次。

头号来源 102.220.161.87，一天打了 360 次被拦请求（/wp-config.php.bak、 /xampp/phpinfo.php、/x.php 之类的自动化漏洞扫描），已封禁并实测生效—— 证据是内核里的规则本身：-A f2b-wb-nginx -s 102.220.161.87/32 -j REJECT， 而不是 fail2ban 自己说"我封了"。

第 4 节三层全绿：451 个文件指纹一致、基线后无文件被写、无任何敏感动作； 服务器 SSH 登录记录为空，密码爆破失败 1 次（密码登录早已关闭）。结论：只被扫，没被打穿。

这个告警本身也被验证过——我造了个假改动

# 往后端源码目录塞一个文件，看它会不会响
touch /opt/wb-api/server/__selftest.tmp
wb-attack -q
→ wb-attack: 关键文件/审计有变动 指纹变更=0 新增=1 删除=0 近期改动=1 审计命中:wb_app_code=1
→ exit=1

# 看门狗跑一次后，时间线里出现条目
[09-19 23:58] 关键文件变动告警：…

# 清理后复查
wb-attack -q  → exit=0（干净）；/var/log/wb-attack.log 0 行

一个假改动被三层同时抓到（指纹新增 + mtime 变动 + audit wb_app_code）， 告警链路确实通到"写进日志"。没验证过的告警等于没有告警，所以这一步必须做。

顺手修掉的两个"会撒谎的告警"

① 5xx 口径错了。第一版统计把 nginx 日志里的响应字节数当成了状态码——错误页正好 548 字节， 于是凭这一串 548 误报出「365 次 5xx」，还给了红了脸的最高级警报。 真相是：唯一真实的 5xx 是 75 次 503，而且全是我自己在做外网压测时被限流拒绝的（UA 是 node）。 现在口径改为：只有 500/502/504 才算故障，503 单列为"限流拒绝（正常）"。

② 审计命中把"我们自己的加固动作"也算进去了。auditd 报出 23:19–23:32 有 wb_sshkey、 wb_nginx 等动作——那些正是我今晚改配置留下的痕迹。天天这么报，报到最后你就再也不看了。 现在只看基线时间之后的动作，并区分高危 key（账户/密钥/代码/模型/云凭据/内核模块）与低危 key （nginx/fail2ban 配置微调），只有高危才触发告警。

一个会误报的告警比没有告警更糟：它训练你忽略告警。这两处都是因为真跑了一遍输出才发现。

已知边界（这一层也不是万能的）

  • auditd 的目录监视不递归：-w /opt/wb-api/server 只盯该目录的直接子项， 子目录里的改动它抓不到 —— 所以才有 A/B 两层做兜底。
  • wb_exec 规则只记录真人登录会话（auid≥1000）发起的执行， 系统服务进程不在覆盖范围内。所以它显示"没有"= 今天没人登录进来执行过东西， 而不是"系统没执行过东西"。
  • 指纹基线不是"清白证明"：它只能证明"和你建基线那一刻相比没变"。 如果入侵发生在建基线之前，基线会把后门一起"认可"为正常 —— 这也是为什么建基线必须选在 确认干净的时刻（本次是在加固完成、清理完测试残留之后）。
  • 告警只写在本机日志（/var/log/wb-attack.log，按月轮转保留 12 个月）， 没有邮件/短信推送。要么靠你偶尔敲一次 wb-attack，要么配阿里云云监控告警 （见第七节待办）。想做到"半夜被打也能叫醒你"，还得走云监控那条路。
本报告所有结论均来自在服务器上的实测输出，未使用推断代替观测；对每一次失败都追到了根因，包括四次由我自己的测试脚本造成的误判。
